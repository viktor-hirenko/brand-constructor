## Выбранный подход

Одна версия = **код ветки стенда** (его три недели смотрели на стенде, и в нём уже перенесены все
правки прода) **+ документы и сценарии `main`**. Получается слиянием `main` в новую ветку
`release/orders`, начатую от ветки стенда. Конфликтные файлы кода решаются в пользу стороны стенда
и проверяются по списку сверки: всё, что `main` меняла, на стороне стенда есть. Этот же коммит
сначала выкладывается на стенд, потом `main` перематывается на него (`--ff-only`) и он же уходит на
прод. На проде оказывается ровно то, что проверено на стенде.

База: структура не меняется. Только шаг данных 013 — брифы «submitted с заказом» → `in_work`,
файлом, сгенерированным по свежему чтению прода (`migrate:013:data`), с предпроверками.

Порядок на проде (как 05.10): копия базы и закладка → сервер → сайт → сразу данные 013 → старый
отдельный визард.

## Что отклонено

- **Выложить ветку стенда на прод как есть, без слияния с `main`.** Guard не пустит (прод — только из
  `main`), а `main` потеряла бы свои документы и сценарии; две истории разошлись бы дальше.
- **Переносить 49 коммитов заказов в `main` по одному (cherry-pick).** Получилась бы новая, нигде не
  проверенная сборка; порция 6 и исправления полного прогона в двух версиях сделаны по-разному и
  конфликтуют почти в каждом шаге.
- **Решать конфликты в пользу `main` и доклеивать заказы.** Код заказов опирается на свои варианты
  общих файлов (порция 6 «с заказами», `W/utils/brief-checks.ts`) — больше ручной работы и риска.
- **Репетировать через `pnpm stage:db:refresh`.** Стирает собственные данные стенда (QA-брифы, архив
  вариантов компонентов). Та же проверка делается на локальной копии прода — так 06.10 гоняли версию прода.
- **Запустить SQL 013/014 целиком.** Поля уже есть — упадёт на «duplicate column».
- **Восстановление базы на закладку (time-travel) как основной откат.** Стирает всё, что люди сделали
  после закладки. Только крайний случай и только по слову владельца.
- **Push на GitHub до приёмки прода.** Пока push не было, `main` возвращается локально.

## Откат

Порядок — как 02.10: **база → сайт → сервер → визард.** Новый код без `in_work` работает, старый
код со статусом `in_work` — нет.

1. `pnpm --filter @brand-constructor/worker db:migrate:013:down:remote` — `in_work` с заказом → `submitted`,
   уже без заказа → `draft`; поля остаются (старый код их не читает).
2. Pages `brand-constructor` → сборка из 2.2 (панель Cloudflare).
3. Worker: `npx wrangler rollback <версия из 2.2> --env production` (в `packages/worker`).
4. Отдельный визард `brand-constructor-app` → сборка из 2.2.
5. Git: до push — `main` на `backup/main-before-orders-<дата>` (сначала ещё один ярлык на текущем
   коммите); после push историю на GitHub не переписывать.

Откат **не** возвращает: отправленные сообщения Slack и задачи Jira; заказы, созданные после
выкладки, станут обычными `submitted` / `draft`; резервы `for_brand_id` останутся и старым кодом не
читаются. Крайний случай — `wrangler d1 time-travel restore` на закладку 2.3, стирает всё после неё;
только по слову владельца.
