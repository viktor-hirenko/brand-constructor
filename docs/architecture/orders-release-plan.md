## Расхождения и решения

Владелец 05.10: «прими решение сам». Решено исполнителем; сессии выкладки по этим пунктам владельца не спрашивать.

1. **«Миграции 013/014 на прод» — их SQL не запускаем.** Колонки уже есть; `ALTER TABLE … ADD COLUMN`
   упадёт на «duplicate column». **Решение:** на прод идёт только **шаг данных 013** (`migrate:013:data` —
   брифы «submitted с заказом» → `in_work`). Если шаг 3.2 покажет, что колонок нет, — выкладку не
   начинать и остановиться: без колонок новый сервер ломает **каждое** сохранение брифа
   (`orders_ready_at` в условии записи), а порядок тогда другой (014 → Worker → Pages → 013 колонки →
   данные 013). Это единственный случай, где сессия возвращается к владельцу до прода.
2. **Шапка `brief-orders-plan.md` (строки 8–11) говорит, что фича на проде** — устарело с отката 02.10.
   **Решение:** поправить в коммите фазы 1.
3. **`pnpm deploy:constructor` и `deploy:all` не передают `--branch main`** — кладут отдельный визард в
   превью, а не в Production (02.10 из-за этого откат до визарда не дошёл). **Решение:** добавить
   `--branch main` в обе команды в коммите фазы 1, рядом с guard: правка в одну строку, а ручной путь —
   место, где ошибаются. В шаге 3.7 — обычный `pnpm deploy:constructor`, после — проверить Production.
4. **`AGENTS.md` и `docs/STATE.md` в `.gitignore`** (`.gitignore:51-52`). **Решение:** в этой выкладке не
   трогаем — к выкладке не относится. Правило «прод из `main`» правим в файле AGENTS §3 на этой машине;
   защиту держит guard в git, он и не пустит выкладку из другой ветки.
5. Скрипт данных 013 не проверяет **оставшиеся резервы** библиотеки (`for_brand_id`) с фаз 2a–4: старый
   код на проде их не читает с 02.10. **Решение:** резерв снимаем (`SET for_brand_id = NULL`), если бриф
   удалён, утверждён, без заказа или элемент уже выбран в другом брифе; резерв брифа с живым заказом
   оставляем. Применяется на стенде (2.4) и тем же списком на проде (3.6), в отчёт — список снятого.
6. **Список брифов для 013 на проде отличается от репетиции.** **Решение:** не останавливаться — скрипт
   считает список одинаково по свежим данным; останавливаться, только если предпроверки скрипта нашли
   битые данные (`brokenStepData`, `nullishOrders`). Список перенесённого — в отчёт.
7. **Push `main` на GitHub.** **Решение:** отдельного слова не ждать — делать сразу после того, как
   владелец принял прод.

## Выбранный подход и что отклонено

**Подход.** `main` перематывается на `feature/brief-orders` (тот же коммит, что уже на стенде),
guard выкладки смотрит на `main`; стенд получает свежую копию базы прода и на ней репетирует данные 013;
владелец проверяет стенд; по «коммит» — коммит guard и документов, по «на прод» — копия базы →
Worker → Pages → данные 013 → отдельный визард. Push `main` на GitHub — после приёмки прода.

Отклонено:
- **Слить в `phase/cleanup` и выкладывать как раньше** — так было 02.10; две «прод-ветки» путают,
  `phase/cleanup` нет на GitHub. Владелец решил перейти на `main`.
- **Слияние с merge-коммитом вместо перемотки** — расхождений нет, перемотка даёт на проде ровно те
  коммиты, что проверены на стенде, без нового непроверенного коммита.
- **Сначала исправления (`fix/wizard-bugs`), потом фича отдельно** — две выкладки и два окна риска;
  порция 5 и проверка H-32 существуют только поверх фичи, на стенде проверялось вместе.
- **Запустить 013/014 «как положено» целиком** — упадёт на существующих колонках (расхождение 1).
- **Откат через восстановление базы на закладку (time-travel restore)** как основной путь — стирает
  всё, что люди сделали на проде после закладки. Только крайний случай и только по слову владельца.
- **Push `main` на GitHub сразу после перемотки** — пока прод не принят, `main` можно вернуть одной
  локальной командой; после push это уже правка истории на GitHub.
- **Удалять `phase/cleanup`** — вне объёма; остаётся как метка «прод до выкладки» (`bb8a0b8`).
- **Выкладывать отдельный визард вручную, как 02.10** — ручная команда и есть то место, где 02.10
  ошиблись; `--branch main` добавляется в скрипт (решение 3).

## Откат

Порядок — как 02.10, проверен тогда на проде: **база → сайт → сервер → визард.** Сначала база: новый
код со статусами после `013_down` работает (просто нет `in_work`), а старый код со статусом `in_work`
не работает.

1. `pnpm --filter @brand-constructor/worker db:migrate:013:down:remote` — `in_work` с заказом →
   `submitted`, уже без заказа → `draft`; колонки остаются (старый код их не читает).
2. Pages `brand-constructor` → сборка из шага 3.1 (`6dd17cd0` или фактическая) — откат в панели Cloudflare.
3. Worker: `npx wrangler rollback <версия из 3.1> --env production` (в `packages/worker`).
4. Визард `brand-constructor-app` → сборка из 3.1 (`69aaaf25`) — в панели.
5. Git: `main` назад не трогаем, если уже на GitHub. Если push ещё не было и от фичи отказываются —
   `git branch -f main fix/wizard-bugs` (исправления без заказов — вариант «отказ от фичи» из
   `wizard-fixes-plan.md`), guard остаётся на `main`.

Что откат **не** возвращает: сообщения в Slack уже отправлены; заказы, созданные за время выкладки,
превратятся в «submitted»/«draft» без «В роботі»; резервы (`for_brand_id`) останутся в базе и старым
кодом не читаются — сделанное для заказа станет видно всем брифам.

Крайний случай — `wrangler d1 time-travel restore brand-constructor-db --env production --bookmark <закладка 3.2>`:
стирает всё, что люди сделали после закладки. Только по слову владельца.
